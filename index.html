Cách setup cập nhật bảng hàng ngày trên Airflow

Giải thích từ khái niệm cơ bản đến recipe thực tế và đánh giá setup hiện tại.

01 Airflow là gì?

Airflow = Công cụ đặt lịch chạy tự động cho data pipeline — khai báo một lần, mỗi ngày nó tự chạy đúng giờ, đúng thứ tự, và báo Slack nếu có vấn đề.

Lý do cần: Mỗi ngày hàng chục bảng cần được cập nhật — xóa số liệu cũ, điền số liệu mới. Làm tay thì dễ quên, dễ chạy sai thứ tự, và không ai biết khi nào thì xong. Airflow giải quyết cả 3 vấn đề đó.

02 DAG là gì?

DAG (Directed Acyclic Graph) = Kịch bản mô tả công việc cần làm theo đúng thứ tự, chạy tự động theo lịch.

Lý do cần DAG: pipeline thường gồm nhiều bước phụ thuộc nhau (xóa trước, rồi mới điền; điền xong mới check). Nếu không có DAG, thứ tự bước phụ thuộc vào người nhớ — sai thứ tự là ra dữ liệu sai. DAG biến thứ tự đó thành code, Airflow tự đảm bảo luôn đúng thứ tự, đúng giờ, và retry đúng bước khi lỗi.

Ví dụ, để cập nhật bảng daily_stock_balance mỗi ngày, cần 2 bước:

Xóa dữ liệu cũ
→
Điền dữ liệu mới

DAG file là file Python mô tả:

  • Lịch chạy: "Chạy lúc 7h30 sáng (0h30 UTC) mỗi ngày"
  • Thứ tự bước: Bước 1 xong rồi mới chạy Bước 2
  • Phản ứng khi lỗi: Gửi thông báo Slack

DAG file không chứa SQL hay logic xử lý dữ liệu — nó chỉ là "kịch bản" nói rằng "làm A rồi làm B".

03 Plugin là gì?

Plugin = File chứa logic xử lý thực sự — câu SQL, hàm tính toán, kết nối BigQuery.

Lý do cần tách riêng: DAG file chỉ nên nói "làm gì, thứ tự nào" — còn làm thế nào (câu SQL cụ thể, logic tính AUM) nên nằm ở chỗ khác để dễ đọc, dễ test, dễ sửa độc lập. Plugin là chỗ đó.

Nếu DAG là kịch bản phim (cảnh 1: xóa, cảnh 2: thêm mới), thì Plugin là diễn viên thực sự lên sân khấu và làm việc đó.

plugins/trading/bigquery_insert_daily_orders_table.pyPython
def insert_table(dataset_name, table_name):
    query = f"""
        INSERT INTO {dataset_name}.{table_name}
        SELECT user_id, date, balance
        FROM raw_mysql.portfolio_transaction
        WHERE date = current_date - 1
    """
    client.query(query).result()

04 Tại sao tách thành 2 file riêng?

Vì lịch chạy và logic xử lý thay đổi vì lý do khác nhau:

DAG filePlugin file
Chứa gìLịch, thứ tự, retrySQL, logic tính toán
Thay đổi khiĐổi giờ, thêm/bớt bướcSửa SQL, sửa logic
Ai sửaNgười setup pipelineNgười viết data

Nếu nhét tất cả vào một file, khi sửa SQL dễ vô tình làm hỏng lịch chạy, hoặc ngược lại.

         ↓ (đến giờ hẹn)
4. Chạy Bước 1: xóa bảng cũ (TRUNCATE)
         ↓
   Chạy Bước 2: điền dữ liệu mới (INSERT)

5a. Thành công → ghi log, chờ hôm sau

08 Hướng dẫn step by step — Thêm bảng mới (Loại A)

1

Tạo bảng trong BigQuery trước

Vào BigQuery console, tạo bảng đích với đúng schema. Bảng phải tồn tại trước — code không tự tạo bảng mới.

2

Tạo file Plugin (chứa SQL)

Tạo airflow/plugins/{domain}/bigquery_insert_{bảng}_table.py:

from google.cloud import bigquery
client = bigquery.Client()

def insert_table(dataset_name: str, table_name: str):
    query = f"""
        INSERT INTO {dataset_name}.{table_name}
        SELECT
            user_id,
            transaction_date,
            SUM(amount) AS total_amount
        FROM raw_mysql.orders
        WHERE transaction_date = DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)
        GROUP BY 1, 2
    """
    client.query(query).result()
3

Tạo file DAG — copy template, đổi 3 chỗ

from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.python import PythonOperator

from trading.bigquery_insert_daily_orders_table import insert_table  # ← ĐỔI
from libs.bigquery_utils import truncate_table
from libs.slack_utils import task_fail_slack_alert

DATASET = "trading"       # ← ĐỔI
TABLE   = "daily_orders"  # ← ĐỔI

default_args = {
    "start_date": datetime(2022, 6, 1),
    "depends_on_past": False,
    "retries": 1,
    "retry_delay": timedelta(minutes=5),
    "on_failure_callback": task_fail_slack_alert,
}

with DAG(
    dag_id=f"schedule_bigquery_{TABLE}_table",
    catchup=False, max_active_runs=1, max_active_tasks=16,
    schedule_interval="45 00 * * *",  # 7h45 sáng VN
    default_args=default_args,
    tags=["bigquery", "reload", TABLE, "schedule"],
) as dag:
    truncate_task = PythonOperator(
        task_id="truncate_bigquery_table",
        python_callable=truncate_table,
        op_kwargs={"dataset_name": DATASET, "table_name": TABLE},
    )
    insert_task = PythonOperator(
        task_id="insert_into_bigquery_table",
        python_callable=insert_table,
        op_kwargs={"dataset_name": DATASET, "table_name": TABLE},
    )
    truncate_task >> insert_task

10 Khi có lỗi — Slack sẽ báo gì?

Mọi DAG đều có on_failure_callback: task_fail_slack_alert. Khi task fail, Slack tự nhận thông báo đỏ. Tên task trong thông báo nói lên ngay vấn đề ở đâu:

Lỗi kỹ thuật (SQL sai, quyền, import thiếu)
🔴 Task Failed
DAG:  schedule_bigquery_reload_daily_stock_balance_table
Task: insert_into_bigquery_table
Time: 2026-09-09 00:47:03 UTC
Log:  http://airflow.internal/log?...task_id=insert_into_bigquery_table
Lỗi data quality (INSERT xong nhưng data bất thường)
🔴 Task Failed
DAG:  schedule_bigquery_reload_daily_stock_balance_table
Task: check_data_quality
Time: 2026-09-09 00:48:21 UTC
Log:  http://airflow.internal/log?...task_id=check_data_quality

ValueError: daily_stock_balance: chỉ có 0 rows hôm nay
  • insert_into_bigquery_table fail → lỗi kỹ thuật, xem log Python/SQL
  • check_data_quality fail → INSERT chạy được nhưng data có vấn đề, xem BigQuery
Viết SQL vào Plugin file, viết lịch chạy vào DAG file, push lên GitHub, Airflow tự làm phần còn lại.

10.2 Lỗi thường gặp khi viết DAG

Variable.get() ở module level — DAG chết không báo rõ lý do

Airflow parse lại tất cả DAG file mỗi 30 giây. Nếu Variable.get() nằm ngoài function, nó chạy mỗi 30 giây — token hết hạn, connection lỗi → DAG tự chết. Thường chỉ thấy task duration 1–2 giây rồi fail mà không rõ tại sao.

# SAI — chạy mỗi 30s khi Airflow parse DAG
token = Variable.get("fb_ads_token")
def my_task():
    call_api(token)

# ĐÚNG — chỉ chạy khi task thật sự execute
def my_task():
    token = Variable.get("fb_ads_token")
    call_api(token)

Credential BigQuery — không hardcode project ID

# SAI — hardcode → 403 Permission Denied khi deploy
client = bigquery.Client(project="anfin-prod-123")

# ĐÚNG — lấy project từ environment
import google.auth
creds, project = google.auth.default(
    scopes=["https://www.googleapis.com/auth/cloud-platform"]
)
client = bigquery.Client(credentials=creds, project=project)

Error capture bằng Variable.set — workaround khi log không đọc được

Khi gặp "Log file does not exist", thêm try/except + Variable.set để capture lỗi — không cần log, không cần kubectl:

def run_task():
    try:
        insert_data()
    except Exception as e:
        Variable.set("error_insert_aum_table", f"{type(e).__name__}: {e}")
        raise  # vẫn raise để DAG báo fail

Đọc lỗi tại: Airflow UI → Admin → Variables → tìm key error_insert_aum_table.

Đây là cách nhanh nhất để debug DAG anfin_daily_aum_per_user hiện tại — thêm Variable.set vào task insert rồi trigger lại, đọc lỗi ngay trong Variables.

10.5 Backfill — Chạy bù dữ liệu lịch sử

Tất cả DAG trong repo đang set catchup=False. Nghĩa là nếu DAG bị tắt 3 ngày, khi bật lại Airflow sẽ bỏ qua 3 ngày đó — không tự chạy bù.

Đây là lựa chọn đúng cho daily reload. Nhưng cần biết cách backfill thủ công khi cần dữ liệu lịch sử.

Khi nào cần backfill?

  • Thêm bảng mới, cần dữ liệu từ 3 tháng trước
  • DAG bị lỗi nhiều ngày, cần chạy lại từ ngày X
  • Sửa logic SQL, cần tính lại toàn bộ lịch sử

Cách backfill thủ công

Cách 1 — CLI (chạy từ trong pod scheduler)

kubectl exec -it airflow-scheduler-0 -n <namespace> -- bash

airflow dags backfill \
  --start-date 2026-08-01 \
  --end-date 2026-08-31 \
  schedule_bigquery_reload_daily_stock_balance_table

Cách 2 — UI (đơn giản hơn cho 1–2 ngày)

Airflow UI → chọn DAG → Grid view → click vào run của ngày cần chạy lại → Clear → DAG sẽ chạy lại ngày đó.

Lưu ý: Backfill chỉ có ý nghĩa nếu pipeline là idempotent (nguyên tắc 1) — chạy lại ngày nào cũng ra đúng dữ liệu của ngày đó.

11 Xem log lỗi ở đâu?

DAG báo lỗi mà không biết lỗi gì — log nằm ngay trong Airflow UI, không phải ở chỗ nào khác.

Cách xem nhanh nhất

Airflow UI → tìm DAG bị lỗi → click run màu đỏ
→ click task đỏ → tab "Log" góc trên phải
→ scroll xuống cuối → tìm "ERROR" hoặc "Traceback"

Nếu không biết Airflow UI ở đâu: hỏi team, port mặc định là 8080.

Các lỗi thường gặp

Dòng lỗi trong logNghĩa là gì
ModuleNotFoundErrorImport thiếu, file plugin không tồn tại hoặc đường dẫn sai
NotFound: 404Tên dataset hoặc tên bảng trong BigQuery không đúng
Forbidden: 403Service account Airflow không có quyền truy cập bảng đó
SyntaxErrorLỗi cú pháp Python trong DAG file hoặc plugin file
ValueError: ...Thường do check thủ công raise lỗi (rows = 0, v.v.)

Trường hợp cụ thể: reload_anfin_daily_aum_per_user_table

DAG này đang fail và log hiện thị: Log file does not exist + Failed to fetch log file from worker. [Errno 2] Name or service not known

Đây không phải lỗi của DAG — log bị mất vì scheduler pod đã restart. Airflow cố fetch log từ pod airflow-scheduler-0 nhưng không kết nối được.

Cách xem log ngay

kubectl exec -it airflow-scheduler-0 -n <namespace> -- bash
ls /opt/airflow/logs/dag_id=schedule_bigquery_reload_anfin_daily_aum_per_user_table/

Hoặc: trigger lại DAG thủ công → vào tab Log ngay khi task đang chạy để xem real-time.

Vấn đề gốc rễ — Log lưu trên pod, pod restart là mất

Fix đúng là cấu hình Remote Logging ra GCS — log được upload lên GCS sau mỗi task, không bao giờ mất dù pod restart:

helm-airflow-prod.yamlYAML
config:
  logging:
    remote_logging: 'True'
    remote_base_log_folder: 'gs://your-bucket/airflow-logs'
    remote_log_conn_id: 'google_cloud_default'

12 Nguyên tắc nền khi setup Airflow pipeline

5 nguyên tắc này áp dụng cho bất kỳ pipeline nào — vi phạm cái nào đều sẽ gặp vấn đề sớm hay muộn.

1. Idempotent — chạy lại bao nhiêu lần cũng ra kết quả giống nhau

Pipeline bị lỗi giữa chừng rồi retry là vấn đề thường gặp. Câu hỏi là: sau khi retry, dữ liệu trong bảng có đúng không?

Nếu vi phạm INSERT không có TRUNCATE trước: lần đầu chạy xong bảng có 1000 rows, retry lần 2 bảng thành 2000 rows — số liệu nhân đôi, dashboard sai không ai biết.

Cách đảm bảo TRUNCATE trước khi INSERT — xóa hết rồi viết lại từ đầu. Chạy lần 1 hay lần 10 thì kết quả như nhau.

Repo này Tất cả Loại A đang dùng TRUNCATE + INSERT — đúng. Nhưng chưa atomic (xem nguyên tắc 2).

2. Atomic — hoặc thành công hoàn toàn, hoặc không có gì thay đổi

Không được có trạng thái "pipeline chạy một nửa". Bảng đang phục vụ dashboard — nếu pipeline fail giữa chừng, bảng phải vẫn có dữ liệu cũ, không phải bảng rỗng.

Nếu vi phạm TRUNCATE xong → bảng rỗng → INSERT bắt đầu → INSERT fail → bảng vẫn rỗng. Airflow retry sau 5 phút nhưng trong 5 phút đó dashboard trả về số 0.

Cách đảm bảo Viết vào bảng tạm trước, chỉ swap sang bảng chính khi tạm đã đầy đủ:

CREATE OR REPLACE TABLE dataset.table_temp AS SELECT ...;
ALTER TABLE dataset.table_temp RENAME TO table;

Repo này Tất cả DAG hiện tại đang vi phạm nguyên tắc này.

3. Tách biệt lịch chạy và logic xử lý

Lịch chạy (giờ nào, retry mấy lần) và logic xử lý (câu SQL, cách tính) là hai thứ thay đổi vì lý do hoàn toàn khác nhau.

Lý do thực tế Người viết SQL không cần biết Airflow. Người setup lịch chạy không cần biết logic tính toán. Tách ra thì hai người làm độc lập, review cũng dễ hơn.

Repo này Đã tách đúng (DAG file và Plugin file riêng). Nhưng SQL đang nhúng trong Python string — không test riêng được, không lint được.

4. Observable — hệ thống phải tự báo khi có vấn đề

Cần phân biệt 2 loại lỗi:

  • Lỗi kỹ thuật: Python crash, SQL syntax sai → Airflow tự phát hiện, Slack báo đỏ ✓
  • Lỗi dữ liệu: 0 rows, null hàng loạt, số giảm bất thường → Airflow không biết, không báo gì ✗

Nếu vi phạm Câu WHERE viết sai, bảng insert 0 rows. DAG vẫn xanh. Slack không báo. Sáng hôm sau mở dashboard thấy số 0, mất nửa ngày tìm nguyên nhân.

Cách đảm bảo Thêm task check sau INSERT: COUNT(*) = 0 → raise lỗi; null hàng loạt → raise lỗi; rows hôm nay < 50% hôm qua → raise lỗi.

Repo này Chưa có lớp kiểm tra nào — đây là điểm thiếu quan trọng nhất.

5. Dependency rõ ràng — bảng nào phụ thuộc bảng nào phải được khai báo

Nhiều bảng dùng kết quả của bảng khác. Nếu không khai báo dependency, tất cả chạy theo giờ cố định và hy vọng bảng nguồn đã xong trước.

Nếu vi phạm Bảng A chạy 7h, thường xong lúc 7h15. Bảng B cài chạy lúc 7h10 nhưng dùng dữ liệu từ A. Hôm A chậm → B chạy khi A chưa xong → B lấy dữ liệu thiếu, kết quả sai.

Cách đảm bảo Dùng TriggerDagRunOperator để B chỉ chạy sau khi A thành công, không phải theo giờ cố định.

Repo này Tất cả DAG chạy theo giờ cố định, không có khai báo dependency nào.

6. SLA / Data freshness — data phải sẵn sàng trước giờ X

Biết pipeline fail là một chuyện. Nhưng pipeline chạy xong muộn hơn cam kết cũng là vấn đề — và Airflow không tự báo khi điều này xảy ra.

Nếu vi phạm DAG chạy lúc 7h, team mở dashboard lúc 8h thấy data thiếu. Airflow không fail, Slack không báo gì. Hoặc pipeline đột nhiên chạy nặng hơn, đến 9h mới xong trong khi báo cáo sáng đã được gửi đi với data cũ.

Cách đảm bảo Khai báo SLA trong DAG:

with DAG(
    sla_miss_callback=sla_miss_alert,
    default_args={
        "sla": timedelta(hours=2),  # task phải xong trong 2h
    }
)

Repo này Chưa có khai báo SLA nào.

7. Lineage — bảng nào từ đâu ra, ai own

Khi có vấn đề data, câu hỏi đầu tiên là: bảng này được tính từ bảng nào? Bảng nguồn đó lại từ đâu? Không có lineage thì tìm root cause mất rất nhiều thời gian.

Nếu vi phạm anfin_daily_aum_per_user bị sai số. Team mất 2 tiếng mới trace ra là raw_transaction bị lỗi từ hôm qua, mà raw_transaction lại lấy từ MySQL pipeline cũng đang có vấn đề.

Cách đảm bảo Tối thiểu: mô tả rõ nguồn dữ liệu trong DAG description. Nâng cao: dùng dbt docs, OpenLineage, hoặc DataHub để tự động track lineage qua các bảng.

Repo này Tags đã có nhưng không đủ để trace. Không có lineage graph.

14 Setup hiện tại cần revamp gì?

🔴 Ngay Setup Remote Logging ra GCS

Log đang lưu trên local filesystem của scheduler pod. Pod restart là mất hết log — không thể debug được gì. Cần bật remote_logging: True và trỏ vào GCS bucket trong Helm config.

🔴 Ngay Đổi password admin webserver

Helm config hiện có username: admin / password: admin. Nếu webserver đang expose qua LoadBalancer mà chưa đổi — vấn đề bảo mật cần xử lý ngay.

🔴 Ngay Thêm data check sau INSERT (vi phạm nguyên tắc 4)

DAG xanh chỉ nghĩa là không có lỗi Python/SQL — không có nghĩa data đúng. 0 rows, null toàn bộ — vẫn xanh. Cần thêm task đếm rows sau INSERT.

def check_table(dataset_name, table_name, min_rows=100):
    count = list(client.query(
        f"SELECT COUNT(*) as cnt FROM {dataset_name}.{table_name}"
    ).result())[0].cnt
    if count < min_rows:
        raise ValueError(f"{table_name}: chỉ có {count} rows")

🟡 Sớm Dùng temp table thay TRUNCATE+INSERT (vi phạm nguyên tắc 2)

Nếu TRUNCATE xong mà INSERT fail, bảng rỗng — dashboard thấy số 0. Nên viết vào bảng tạm trước, thành công rồi mới swap sang bảng chính.

CREATE OR REPLACE TABLE dataset.table_name_temp AS SELECT ...;
ALTER TABLE dataset.table_name_temp RENAME TO table_name;

🟡 Sớm Thống nhất tên DAG

Cùng 1 repo có 3 kiểu đặt tên. Nên chọn 1 convention: {domain}__{table}__{frequency} ví dụ trading__raw_transaction__daily

🟠 Khi có time Tách SQL ra file .sql riêng

SQL đang nhúng trong Python string — không test riêng được, không lint được, review khó. Nên tách ra plugins/{domain}/sql/{table}.sql.

🟠 Khi có time Khai báo dependency giữa DAG (vi phạm nguyên tắc 5)

Nhiều bảng phụ thuộc nhau nhưng tất cả chỉ chạy theo giờ cố định. Nên dùng TriggerDagRunOperator hoặc Airflow Dataset.

🟡 Sớm Dùng partitioned table trong BigQuery

TRUNCATE + INSERT trên bảng không partition = BQ scan toàn bộ bảng mỗi ngày. Bảng càng lớn, tiền càng nhiều, query càng chậm. Nên partition theo ngày và chỉ replace đúng partition hôm qua — không cần TRUNCATE, idempotent, rẻ hơn nhiều.

-- Chỉ ghi vào partition ngày hôm qua, không ảnh hưởng các ngày khác
INSERT INTO dataset.table
SELECT ...
WHERE date = DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)

🟡 Sớm Khai báo SLA trong DAG

Hiện tại không biết khi nào pipeline chạy muộn — chỉ biết khi fail. Cần khai báo SLA để Airflow alert khi task vượt quá thời gian cho phép.

🟠 Khi có time Xử lý schema evolution

Khi MySQL thêm/bớt cột, pipeline Loại B/C có thể fail hoặc tệ hơn — chạy xanh nhưng bỏ sót cột mới. Cần thêm bước kiểm tra schema hoặc bật ALLOW_FIELD_ADDITION trong BQ load config.

🟠 Khi có time Cost monitoring BQ

BigQuery tính tiền theo lượng data scanned. SQL viết sai (thiếu WHERE, không dùng partition) có thể scan TB dữ liệu mà không ai biết cho đến khi thấy hóa đơn. Cần set maximum_bytes_billed và bật budget alert trên GCP.

🟠 Khi có time Lineage documentation

Hiện tại không có cách trace nhanh "bảng này tính từ bảng nào". Tối thiểu: thêm mô tả nguồn dữ liệu vào DAG description. Nâng cao: dùng dbt docs hoặc OpenLineage.

🟠 Khi có time Connection management

SSH key cho git-sync đang lưu trong K8s secret airflow-gke-git-secret. Service account key cần được rotate định kỳ. Nên xem xét dùng Workload Identity (GKE) thay vì key file — không cần lưu key ở đâu cả.

⚪ Dài hạn Cloud SQL + CeleryExecutor

LocalExecutor ổn hiện tại nhưng scheduler đang cấp 10GB RAM. PostgreSQL built-in tự ghi "not recommended for production" trong helm chart. Nên chuyển sang Cloud SQL và xem xét CeleryExecutor.

15 Data Quality — kiểm tra dữ liệu sau khi chạy

Data Quality = Lớp kiểm tra tự động để phát hiện data sai trước khi lên dashboard.

Lý do cần: Airflow chỉ biết Python có crash hay không — không biết bảng có 0 rows, user_id bị null toàn bộ, hay số liệu giảm 90% so với hôm qua. Không có data quality check thì pipeline xanh nhưng dashboard sai, và thường mất nửa ngày mới phát hiện ra.

Có thể bảng có 0 rows vì câu WHERE quá chặt, cột bị null toàn bộ vì join sai, hoặc số giảm bất thường vì source có vấn đề — Airflow vẫn xanh, Slack không báo gì.

Lớp 1 — Kiểm tra cơ bản (nên có ngay)

Thêm task sau INSERT, raise lỗi nếu bất thường:

def check_data_quality(dataset_name, table_name):
    query = f"""
        SELECT
            COUNT(*)                              AS total_rows,
            COUNTIF(user_id IS NULL)              AS null_user_id,
            COUNTIF(date < '2020-01-01')          AS invalid_date
        FROM {dataset_name}.{table_name}
        WHERE date = DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)
    """
    row = list(client.query(query).result())[0]

    if row.total_rows == 0:
        raise ValueError("Bảng không có dữ liệu hôm nay")
    if row.null_user_id > 0:
        raise ValueError(f"Có {row.null_user_id} rows bị null user_id")

Flow mới: truncate >> insert >> check_data_quality

Lớp 2 — So sánh với hôm qua (nâng cao)

SELECT
    today.total_rows,
    yesterday.total_rows AS yesterday_rows,
    SAFE_DIVIDE(today.total_rows, yesterday.total_rows) AS ratio
FROM
    (SELECT COUNT(*) AS total_rows FROM dataset.table WHERE date = CURRENT_DATE - 1) today,
    (SELECT COUNT(*) AS total_rows FROM dataset.table WHERE date = CURRENT_DATE - 2) yesterday

Nếu ratio < 0.5 (hôm nay chỉ bằng 50% hôm qua) → raise lỗi.

Lớp 3 — dbt tests (dài hạn)

Nếu có dùng dbt, nó có sẵn framework test: not_null, unique, accepted_values, relationships. Đây là cách chuyên nghiệp nhất để quản lý data quality ở quy mô lớn.

15b Daily Monitoring DAG — tóm tắt pipeline qua Slack

Khi chạy 100 bảng mỗi ngày, cần một DAG riêng chạy sau tất cả và gửi 1 tin Slack tổng hợp: bao nhiêu bảng thành công, bao nhiêu fail, và lỗi cụ thể là gì.

Cách hoạt động

Bước 1 — Mỗi DAG business capture lỗi vào Variable

Trong task của tất cả DAG bình thường, thêm try/except ghi lỗi ra Variable với key chuẩn error__{tên_bảng}:

plugins/trading/bigquery_insert_raw_transaction_table.pyPython
def run_insert(dataset_name, table_name):
    try:
        # ... logic insert ...
        Variable.delete(f"error__{table_name}")   # xóa lỗi cũ nếu success
    except Exception as e:
        Variable.set(f"error__{table_name}", f"{type(e).__name__}: {e}")
        raise

Bước 2 — Monitoring DAG đọc Variable và gửi Slack

dags/monitoring/daily_pipeline_summary.pyPython
from airflow.models import Variable, DagRun
from airflow import settings
import requests

SLACK_WEBHOOK = Variable.get("slack_webhook_monitoring")
TABLES = [
    "raw_transaction",
    "daily_stock_balance",
    "trader_churn_status",
    "anfin_daily_aum_per_user",
    # ... list toàn bộ bảng
]

def send_daily_summary():
    session = settings.Session()
    today = datetime.utcnow().date()

    dag_runs = session.query(DagRun).filter(
        DagRun.execution_date >= today
    ).all()
    run_map = {run.dag_id: run.state for run in dag_runs}

    failed, success_count = [], 0
    for table in TABLES:
        dag_id = f"schedule_bigquery_reload_{table}_table"
        state = run_map.get(dag_id)
        if state == "failed":
            error = Variable.get(f"error__{table}", default_var="(không rõ lỗi)")
            failed.append({"table": table, "error": error})
        elif state == "success":
            success_count += 1

    total, fail_count = len(TABLES), len(failed)

    if fail_count == 0:
        text = f"✅ *Daily pipeline report · {today}*\nTất cả {total} bảng chạy thành công."
    else:
        lines = [f"🔴 *Daily pipeline report · {today}*",
                 f"*{total}* bảng chạy  ·  *{success_count}* thành công  ·  *{fail_count}* thất bại\n"]
        for f in failed:
            lines.append(f"• `{f['table']}`\n  _{f['error']}_")
        text = "\n".join(lines)

    requests.post(SLACK_WEBHOOK, json={"text": text})
    session.close()

with DAG(
    dag_id="monitoring_daily_pipeline_summary",
    schedule_interval="30 2 * * *",   # 9h30 sáng VN — sau khi tất cả DAG 7h-8h đã xong
    catchup=False,
    default_args={"start_date": datetime(2026, 1, 1)},
    tags=["monitoring", "slack"],
) as dag:
    PythonOperator(task_id="send_slack_summary", python_callable=send_daily_summary)

16 Môi trường Dev và Prod

Dev/Prod = Hai bản chạy riêng biệt của cùng một pipeline, trỏ vào dataset khác nhau.

Lý do cần tách: Hiện tại mọi thay đổi đang test thẳng trên production — viết sai SQL là bảng production bị ảnh hưởng ngay, không có chỗ thử an toàn. Với Dev environment, developer test thoải mái trên dataset trading_dev trước, chỉ merge vào main khi đã ổn.

Cách implement

Repo đã có sẵn Variable.get("env") — GCS bucket đã dùng pattern này. Chỉ cần mở rộng ra BigQuery dataset:

from airflow.models import Variable

ENV = Variable.get("env", default_var="dev")  # mặc định dev cho an toàn

def get_dataset(base_name: str) -> str:
    if ENV == "prod":
        return base_name
    return f"{base_name}_{ENV}"   # → "trading_dev"

Và git branch strategy: mọi thay đổi đi qua develop trước, chạy ổn trên dev rồi mới merge vào main.

17 CI/CD là gì?

CI/CD (Continuous Integration / Continuous Deployment) = Hệ thống tự động kiểm tra và triển khai code mỗi khi có thay đổi, thay vì làm tay.

CI — Chưa có

Tự động chạy kiểm tra khi có Pull Request — syntax, import, DAG parse — trước khi code vào main. Lý do cần: không có CI thì code sai syntax vẫn merge được, chỉ bị phát hiện sau khi Airflow đã deploy và DAG fail trên production.

CD — Đã có ✓

git-sync kéo code từ main về mỗi 60 giây, DAG tự xuất hiện trên Airflow. Lý do cần: deploy tay dễ quên, dễ nhầm version, dễ thiếu file khi nhiều người thay đổi DAG cùng lúc.

Nếu muốn thêm CI, dùng GitHub Actions để chặn lỗi syntax trước khi vào main:

python -m py_compile airflow/dags/**/*.py  # kiểm tra syntax
airflow dags list                           # kiểm tra DAG parse được
